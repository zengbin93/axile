01 · 整体设计：账户控制，不只是“每秒限流”

核心目录为 axile/executor/account_control/。模块把操作声明、策略配置、运行时准入、行为留痕与持久化恢复分开，服务于单次 execution。它采用固定分钟/自然日计数桶 + 上次放行时间间隔，不是令牌桶，也不是分布式限流服务。

注册 operation / group→默认空规则 + preset + override→加载数据库快照→绑定 guard→排队 / 检查 / 预占→调用 SDK→回填 outcome→请求结束时刷盘

1.1 定义层与配置层

  • AccountControlRegistry 保存操作键及其共享组。装饰器在函数定义时登记；CTP 专用叶子操作由 ctp_operations.py 显式登记。bootstrap 用于恢复导入声明。
  • resolve_account_control_policy(preset_key, override) 先为注册操作生成空规则，再叠加 preset，最后逐字段叠加账户 override。注册本身不意味着存在有限额度。
  • 作用域是 operations.<op>.account、operations.<op>.symbol 和 groups.<group>；规则为 per_minute、per_day、min_interval_ms。任一 scope 阻断则整体阻断；多个等待规则取最长等待。
  • CTP 共享组成员不是写在所有操作的注册定义里，而由 EffectiveAccountControlPolicy.operation_groups 补充。guard 取注册组与策略组的并集。切换 preset 会改变成员关系。
  • 数字采用严格整数与非负校验；时区校验基于 ZoneInfo；最小间隔必须为正数。unlimited=true 只允许解除分钟/日额度，与 limit/on_trigger 互斥。省略或 null 表示继承，不表示解除。最小间隔不允许 unlimited，但可以下调到 1ms。

1.2 运行时、调度与计数语义

begin_operation() 在 guard 内部使用 RLock 将“检查 + 预占”做成临界区。排队键是 (priority, seq)，数字越小优先级越高，同级 FIFO；只有队头评估额度。等待时释放状态锁，默认每 100ms 轮询，并调用 termination checkpoint。

allow立即增加 account 的分钟/日计数；配置了 symbol scope 才存 symbol 计数；记录 pending 事件，返回 Attempt。
wait不扣次数，不立即写事件；轮询直到允许或阻断。放行后记录累计 waited_ms、命中 rules、priority、groups。
block记录 blocked / counted=false / policy_blocked；抛出 AccountControlBlockedError，SDK 不被调用。

装饰器和 run_controlled_call 在真实方法返回后回填 outcome；普通异常记录 downstream_error 并原样抛出。已经放行的失败请求不退额度，所以计数代表“准入尝试”，不等同于成交、柜台受理或实际网络发包次数。参数验证也可能在准入后才失败。

依据：guard.py:377、guard.py:610、guard.py:776、decorators.py:39（本节短路径均位于核心目录）。

1.3 生命周期与持久化

  • 服务端构造 guard 时读取当天累计计数，以及历史最近一次 allowed+counted 时间。account_id、execution_id、policy 任一为 None 时 guard 是 no-op；包装器 guard=None 也直接调用下游。
  • 内置 CTP、GM、TQ 均声明 process 后端。worker 逐请求重绑 guard、审计与 runtime；资产查询使用 request_id 作为 execution_id。CTP 支持先绑定 guard 再建立连接；不要把专用 worker 资产查询误判成漏绑定。
  • 普通执行路径的 initialize_executor_runtime 同样先挂 guard，再初始化需要 pre-connect guard 的渠道。set_account_control_guard 同时注入终止检查点。
  • flush_records() 返回本次 execution 的累计快照，不清空内存。每个 bucket/scope/operation 的 delta_uid 固定，event_uid 由 execution/seq/operation/symbol/decision 组成。
  • AccountControlStore.flush_execution_records 在一个 SQLite 事务中批量 INSERT OR IGNORE。重复同一最终快照是幂等的；持续增长的快照重复刷盘不是正确的增量协议（R3）。当前主要刷盘点是结束、清理和初始化失败。

依据：axile/server/execution/execution_account_control.py:17、axile/server/execution/lifecycle.py:382、axile/server/execution/worker_backend/worker_state.py:242、axile/server/execution/worker_backend/worker.py:134、axile/server/account_control/store.py:146。

1.4 时间语义与边界

默认使用 Asia/Shanghai 的自然日午夜和整分钟边界，不使用 CTP TradingDay，不实现滚动 60 秒窗口。夜盘与次日日盘可能属于同一交易日，却处于不同 control_date。跨 execution 的最小间隔能从事件恢复；共享组通过成员操作的最近放行时间恢复，不依赖独立持久化组计数。墙上时钟的前跳/回拨会影响间隔；允许切换时区，但桶键不含 UTC offset，夏令时回拨地区存在重名分钟。

2.1 服务端调用范式

from axile.executor.account_control import ensure_account_control_preset_compatible
from axile.server.execution.execution_account_control import (
    build_account_control_guard, flush_account_control_records,
)
from axile.server.execution.factory import create_executor_instance, initialize_executor_instance

ensure_account_control_preset_compatible(account.account_control_preset, account.trade_channel)
executor = create_executor_instance(account, initialize=False)
try:
    guard = await build_account_control_guard(account, execution_id)
    executor.set_account_control_guard(guard)
    if getattr(executor, "_requires_connection_initialization", False):
        initialize_executor_instance(executor)
    # 交易生命周期应交给现有 server/worker 编排；同步调用在其工作线程执行。
    # 通过 executor.place_order / cancel_order / query_trades 调用，勿绕至 _impl。
finally:
    try:
        await flush_account_control_records(executor)
    finally:
        executor.stop()

此片段说明绑定顺序，不是另造一条并发执行通道。生产应复用 initialize_executor_runtime / _resolve_prepared_executor，连同账户占用、termination controller、审计、失败清理一起使用。直接构造执行器不会自动恢复额度。

2.2 覆盖配置示例

{
  "operations": {

      "account": {

        "per_day": {"limit": 3000, "on_trigger": "block"},

仅为配置结构示例，数值不是 GM/TQ 柜台官方限额。新增操作应先注册，再配置，再覆盖所有真实 SDK 调用路径；仅在编辑器里添加一条 query_account 规则，不能让未经过 guard 的 GM get_cash 自动受控。

2.3 对外 HTTP 与用户界面

账户路由相对路径 /{account_id}/control/policy 是只读预览，返回兼容 preset、override、preset/effective policy、操作及共享组元信息。修改通过已有账户创建/更新接口完成。审计提供 /{account_id}/control/audit/summary、/{account_id}/control/audit/executions 和 /executions/{execution_id}/control/events。预览接口通过操作元信息保留组成员，但返回的基础 Policy 本身不含 operation_groups；不要拿它直接构造执行 guard。

四个常见误用：注册即限流；recorded 即受限；accepted 即成交；重复 flush 即可靠增量。四者在当前代码中均不成立。

03 · 全渠道调用覆盖矩阵

“覆盖”分四类：受有限规则保护 仅记录 / 无有限规则 未进入统一 guard 本地读取 / 独立控制面。下表针对正常公开调用及 worker 生命周期；直接调用私有方法不属于安全公开入口。

3.4 跨渠道入口、批量操作与扩展

ExecutionSession 调用 owner 的公开 facade，内部共享查询只有 leader 包装，回调失效会触发下一次真实抓取；不能只统计装饰器数量。cancel_all_orders 通过公共查单和逐单撤单；清仓进入既有执行引擎而非新的 SDK 批量下单入口。仓库只内置 CTP、GM、TQ；外部 ChannelPlugin 必须遵守 facade/guard 约定，不能声称其实现已审查。

通用 inline 资产服务 axile/server/account_assets.py:19 直接构造执行器且未挂 guard，是thread 后端扩展风险。三个当前内置插件全走 process，worker 对资产请求已绑定有效 request_id，因此不是三个内置渠道当前普遍漏绑定。

04 · 风险清单与可复现证据

11 项合并后的风险主题；含已证实缺陷、配置缺口、条件性风险。
10 项失败断言运行 --runxfail 直接观察失败，不以“已有测试通过”推断安全。
252 passed相关回归套件；另有 10 strict xfailed，代表尚未修复。

优先级不是柜台事故概率预测。P1＝可能绕过预期安全边界或丢失计数；P2＝可靠性/扩展/审计问题。真实柜台 QPS、前置并发窗口和监管日额度没有本地实盘证据；1500ms 是项目 preset，不是对所有柜台的合规保证。

P1 · 覆盖遗漏 / 已证实

R1 · GM 的资金、持仓、行情未走 guard，成交查询只有记录没有限额

根因：GM 的 _call_bridge 只转发 SDK；get_account_assets/current/卖出持仓检查未包相应 operation。query_trades 则有包装，但注册默认 scope 全空，default preset 未补规则。用户给 query_account 配置限制，也拦不住实际 GetCashRequest。

触发与影响：主动资产刷新、频繁行情快照或成交缓存失效可持续调用 SDK；统一策略 UI 的配置与实际保护不一致。SDK 自身是否缓存、是否另有限额不能消除“Axile 没有此项控制”的事实，但本报告不据此断言一定发生网络超限。

证据：渠道矩阵所列 GM 三处调用路径；新增参数化测试 test_gm_asset_queries_obey_zero_operation_quota 在 query_account/query_positions 设置 0/day 时，真实公开 get_account_assets 仍调用 SDK stub 的 get_cash/get_position。test_default_trade_queries_are_recorded_without_a_finite_rule 证实成交三个规则均为 None。原有成交查询测试仅验证预算事件，而非有限额度。

建议与验收：明确 GM 物理请求操作与业务操作的分层，在唯一叶子桥接入口加准确映射和合理 preset；对资金/持仓/current/get_execution_reports 做“阻断后 SDK stub 调用次数为 0”的测试。行情请求需考虑批量 symbol 成本。TQ 本地快照不应被同一修复误伤。

P1 · 配置逃逸 / 已证实

R2 · CTP 总间隔依赖可选 preset，所谓“硬保护”仍可下调到 1ms

根因：default 对 CTP 兼容，而 CTP TraderApi 操作注册的 groups 为空；只有 ctp preset 赋予 ctp_td_global 成员。账户 override 又可覆盖 min_interval_ms 为任意正整数。

复现：test_default_preset_on_ctp_does_not_attach_trader_group 中 query_account、query_positions 在同一时间放行；test_ctp_group_interval_can_be_lowered_to_one_millisecond 中最终间隔为 1。两项为刻画现状的通过测试，不是假装整改完成。

边界：内置 CTP 新账户默认选 ctp，已有迁移也设置该 preset；风险在合法选择 default 或显式降低配置时出现，而不是默认路径完全没有流控。

建议与验收：产品确认这是可调建议值还是柜台安全底线；若是底线，分离不可解除的渠道 envelope 与可覆盖的业务额度，并在账户更新、worker 装配和预览层一致校验。最低值需按柜台配置确认，不能凭本报告硬编码。

P1 · 持久化协议 / 已复现

R3 · 增长中的累计快照重复 flush，后续计数和 outcome 被忽略

根因：guard.py:717 为同一 bucket 生成固定 delta_uid；store.py:146 的 OR IGNORE 对已有记录不更新。第 1 次 flush 写 delta=1 与 pending；再发生请求并更新 outcome 后，第 2 次 flush 的 delta=2 和 fetched 被忽略。

复现：隔离 SQLite 的两项参数化安全测试分别得到 count=1（应为 2） 与 outcome=pending（应为 fetched）。当前主要是最后刷盘，故正常一次最终 flush 不触发此问题；未来周期刷盘、并发清理或先导出再继续使用 guard 会触发。

建议与验收：选择单调累计 upsert（防止旧快照回退）或带独立 UID 的真正增量/watermark 协议，事件 outcome 也需定义终态更新顺序；覆盖相同快照重试、增长快照、乱序快照、并发 flush、事务失败重试。不能直接改为每次累加完整 delta，否则会重复计数。

P2 · 异步公共 API / 已复现

R4 · async 包装器在 await 前同步等待，阻塞事件循环

根因：decorators.py:105 直接调用同步 guard.begin_operation，后者使用 sleep 轮询。async 只体现在执行 downstream 时的 await。

复现：先耗用 CTP 组额度，再将 heartbeat 用 loop.call_soon 排入队列。第二次异步查询等待结束并进入下游时，heartbeat 尚未执行；await sleep(0) 后才执行。测试用虚拟时钟，无真实长时间等待。

影响边界：当前三个 SDK 主路径多在同步 worker，不代表现有全部交易都会卡 FastAPI；直接使用该公开 async API 的插件或协程任务会阻塞同 loop 的取消、心跳和其他请求。

建议与验收：实现异步原生等待队列/条件唤醒，并共享原子准入；若使用线程桥接，必须处理取消后后台线程继续申请额度甚至发送的问题。测试 heartbeat、公平性、取消移除、无 orphan send。

P2 · 扩展 fail-open / 已复现

R5 · 未知 operation 静默放行；冻结后的迟到声明也不报错

根因：guard.py:412、:784 对不存在 operation 使用空 AccountControlOperationPolicy；配置入口虽然 require_operation，但运行时不执行相同校验。decorator_registry.py:59 在 frozen 且未知时直接返回描述，不注册也不拒绝。

复现：query_acount_typo 下游正常执行且记 allowed；隔离冻结注册表后提交 late_audit_operation 未抛异常。两项严格 xfail 分别覆盖。

附带静态发现：registry 文档声称执行前冻结，但生产没有调用 freeze；operations/groups 返回内部 dict。内置固定字符串暂未发现拼错，但插件迟到导入、规则快照形成后再增操作会扩大风险。

建议与验收：在准入前 require_operation；启动完成时校验 registry/policy 一致性；冻结后未知声明必须报错；只读映射或副本保护注册表。隔离测试覆盖不同导入顺序和动态插件启动失败。

P2 · 等待活性 / 已复现 + 静态推导

R6 · 0/day + wait 永远无法满足；队头等待牵连无关操作

根因：guard.py:862 日规则没有“limit=0 立即 block”的特殊处理，分钟规则却有；0/day 在每个自然日都满足 count≥0，因此无法放行。guard 没有内置总等待上限。

复现：合法 policy 设置 0/day+wait；测试用第 3 次 checkpoint 主动中止，观察到没有 AccountControlBlockedError。不是让测试无限挂起，而是验证始终进入等待路径。

队头影响：同一 guard 只有全局队头评估；同级先来的 place_order 在等待自己的独立规则时，后到的 cancel_order 不能利用自己的空闲额度。default 的两者 priority=100；ctp 的 cancel=0 优先于 place=10，部分缓解。持续高优先级也可能饿死低优先级。

建议与验收：配置拒绝不可能等待的规则，或一致地立即阻断；对独立可满足规则做 ready-aware 调度/分组排队，加入 aging 与总 deadline。测试无关组并发、撤单应急优先级、终止中断和无限高优先级流量。

P2 · 审计失真 / 已复现

R7 · 取消、回填失败和异步柜台拒绝未统一闭合事件

根因：包装器只捕获 Exception；async CancelledError 不在此捕获范围，记录保留 pending。success_outcome/result_metadata_resolver 在调用 try 块之外运行，resolver 失败也可能让成功发单后的流控事件停留 pending。CTP accepted 是同步请求 return_code=0，之后的拒绝回报更新订单/期权状态，不会自动回写流控事件。

复现：异步下游抛 CancelledError 后，已放行事件 outcome 仍为 pending。另两条为静态路径核查，未模拟真实柜台拒绝。取消异常必须仍向上传播，不能为了记事件吞掉取消。

建议与验收：区分 quota_decision、dispatch_status、business_status；明确 cancelled/unknown_send/outcome_record_error，使用稳定 request/order 关联。验证 SDK 已发送但回填失败不会诱发业务盲目重试；结合 R3 修正重复 flush 的终态更新。

P2 · 发包边界 / 条件性已复现

R8 · 限制的是“准入时刻”，不是相邻真实 SDK 发送时刻

根因：guard 在进入 call 前记录 last_allowed。CTP place_order 额度位于 facade，后面还有校验、订单构造、线程调度；GM/TQ 还有 bridge 排队。若第一个调用在本地停顿超过间隔，第二次准入可以紧接第一次真正发送。

复现：共享组要求 1.5 秒；第一个受控 call 在发送前用虚拟时钟推进 2 秒，第二个调用立即发送。两次记录的“发送时刻”间隔为 0。该复现证明包装器不保证物理发送间距，不声称生产柜台已出现超限。

建议与验收：业务准入和物理发包节流分层，SDK owner/发送仲裁器在唯一发送边界预占物理请求预算；不要粗暴把所有 facade+叶子重复绑定同组。测试本地准备延迟、owner 队列拥塞、多线程抢占、连接回调与交易并发。

P1 · 崩溃恢复 / 多实例边界

R9 · 内存预占与结束刷盘不是跨进程、跨应用实例的账户总量保证

证据：每个 guard 拥有独立锁和 baseline；两个相同账户空基线 guard 在 1/day 限额下都能放行（新增刻画测试）。实际服务器的账户占用注册和每账户 worker 降低同进程并发，不等于跨两个 Axile 进程、两条账户配置指向同一柜台账户、或其他交易终端的统一锁。

崩溃窗口：下游发单成功后若进程在最终 flush 前被 kill，内存计数和事件丢失；重启按旧数据库恢复，可能重复获得当天额度。此项由写入时点推导，未执行进程 kill 或实盘事故实验。

建议与验收：先明确部署不变量：单实例/账户唯一身份映射/worker 串行。若要求强账户级保证，需要持久化预占或单一账户仲裁服务、故障恢复/幂等令牌和 unknown-send 状态。周期 flush 只能缩短窗口，且必须先修 R3；本地总量仍无法涵盖其他软件的柜台操作。

P2 · 渠道语义不匹配

R10 · TQ 本地查单被限成远端查询；共享 UI 暴露未接入操作

TqSdk 锁定版本的 get_order/get_trade/account/position 从内存 Entity 取值。公共 query_order 仍会扣 default 的分钟/日额度，并受 account 100ms、symbol 300ms 间隔约束，可能延迟纯本地监控而不降低柜台压力。query_trades 却不限，说明公共查询策略并未按请求成本统一设计。

策略预览列举所有 registry 操作，不按当前 channel 的真实实现过滤；GM/TQ 能看到 CTP 专属操作，CTP 的 query_settlement_info 当前没有实际调用。配置看似成功，不代表业务已接入。

建议与验收：分离本地 query snapshot 与 remote request 额度；channel contribution 声明支持的操作、真实成本和适用组。UI 显示“不支持 / 仅审计 / 远端限速”状态。不要简单移除全部查询控制，CPU/内存负载需要另一类保护。

P2 · 时间、容量与可观测性边界

R11 · 固定自然日、墙钟与无界记录需要明确运行上限

  • 自然日与期货交易日不同；如果 per_day 的产品承诺是 TradingDay，则夜盘跨午夜会提前恢复额度。当前模型文字明确自然日，是否改动属于需求确认，不直接判作算法 bug。
  • min_interval 使用 wall time；前跳可提前准入，回拨拉长等待。非上海时区的 DST 重复分钟会使用同名 naive bucket。需要 wall time 分桶 + monotonic elapsed，恢复时明确两者换算。
  • 事件、历史 bucket、队列在 execution 内无独立容量限制；每次 flush 导出所有记录，并单条多值 INSERT。长会话/无限额度可能增加内存、锁占用及 SQLite 参数数量压力；具体参数上限取决于 SQLite 构建，本次未做大规模压测。
  • 等待取消时没有必然的专属等待事件；waited_ms 是计划 sleep 累加，含非队头排队但不含全部真实延迟。仅看最终 allowed 日志可能看不到一直等待后取消的请求。

建议与验收：约定交易日/自然日合同；注入时钟测试前跳、回拨、DST、跨日恢复；设置合理 execution/队列/事件上限与归档；分批事务写入同时保留幂等语义。容量、时间与中断问题分别测试，不用一个“慢测试”替代。

06 · 建议整改顺序、验收与回滚

阶段范围验收 / 风险控制
先确认产品契约CTP 底线可否调低？per_day 是自然日还是交易日？哪些额度是业务保护、哪些是柜台物理请求保护？是否承诺多实例同账户？不能未经确认直接给全渠道套一个固定 QPS，或为撤单全面禁用风控。文档与配置编辑器同步契约。
第一批：覆盖与可靠记录R1 GM 请求映射；R2 渠道 envelope；R3 累计持久化协议；R5 unknown operation 校验阻断后 SDK 0 调用；同一快照重试不翻倍；增长/乱序刷盘不丢数；未知操作 fail-fast。保留旧账户配置解析和迁移校验。
第二批：调度与发送边界R4 async；R6 公平性/零额度；R8 SDK owner 发包仲裁取消不会留后台发送；应急撤单可抢占但不能突破物理间隔；通过虚拟时钟与确定性事件同步验证，避免 sleep 猜时间。
第三批：审计与系统边界R7 状态关联；R9 持久化预占/多实例；R10 渠道 UI；R11 时间和容量定义 unknown-send 恢复、时间基准、容量上限；故障注入和沙箱压力测试，最后才在获授权的券商测试环境核对真实限额。
